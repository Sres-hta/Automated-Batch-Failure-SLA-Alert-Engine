1. Executive Pitch & Banking Business Context (The "Why")

🎙️ 30-Second Elevator Pitch (Memorize this for "Tell me about your project"):

"I built FinOps-BatchGuard, an enterprise-grade batch execution, auto-recovery, and SLA alert engine modeled after Hitachi JP1 and BMC Control-M used in core banking operations. It orchestrates critical overnight batch workflows like SWIFT feed ingestion and EOD settlement. When transient database lock contention hits, it executes auto-retry with exponential backoff. When a hard deadlock occurs, it halts downstream regulatory reports to prevent corrupted ledger filings and leverages ITIL v4 rules to auto-generate structured ServiceNow incident tickets (INC0010xxx) with parent-child correlation—completely eliminating false P1 alert floods. Finally, it executes real Unix infrastructure health checks and automatically compiles an executive shift handover check-sheet in CSV and dark-themed HTML for the incoming morning operations team."

⏱️ 2-Minute Deep-Dive Walkthrough:

In a tier-1 financial institution like MUFG, overnight batch operations run between 22:00 and 06:00 to balance multi-currency books, settle transactions, and transmit statutory returns to central banks (MAS in Singapore, Federal Reserve in the US). In legacy operations, teams suffer from alert storms (when one upstream failure triggers dozens of downstream P1 alarms), transient false alarms (minor lock contention waking on-call teams), and unnoticed SLA breaches on recovered jobs.

FinOps-BatchGuard solves this through 4 integrated stages: pre-flight Unix system housekeeping (disk, memory, daemons), DAG dependency orchestration with retry backoff, ITIL v4 incident routing with automated parent-child correlation, and automated shift handover report generation.

3. File-by-File & Function-by-Function Code Walkthrough

src/engine.py: Topological Sorting & Subprocess Execution

Key function: resolve_execution_order() implements Kahn's algorithm for topological sorting to guarantee valid DAG execution:

# In src/engine.py: Kahn's Algorithm for Topological Sort
def resolve_execution_order(self) -> List[Dict[str, Any]]:
    job_map = {job["job_id"]: job for job in self.jobs}
    in_degree: Dict[str, int] = {job_id: 0 for job_id in job_map}
    adj_list: Dict[str, List[str]] = {job_id: [] for job_id in job_map}

    for job_id, job in job_map.items():
        for upstream in job.get("depends_on", []):
            adj_list[upstream].append(job_id)
            in_degree[job_id] += 1

    queue = [job_id for job_id, deg in in_degree.items() if deg == 0]
    ordered_ids = []

    while queue:
        queue.sort()  # Guarantees deterministic order
        curr = queue.pop(0)
        ordered_ids.append(curr)

        for neighbor in adj_list[curr]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)

    if len(ordered_ids) != len(job_map):
        raise ValueError("Cyclic dependency detected in batch schedule configuration.")
    return [job_map[jid] for jid in ordered_ids]

4. The 3 Core Operational ITIL Rules (Deep Dive)

🚨 Rule A: Hard Failure ➔ P1 Major Incident Bridge

Condition: status == 'FAILED' (e.g., JOB_03_EOD_SETTLEMENT, Exit Code 2).

Action: Generates INC0010404 (Priority: P1 - Critical, State: Assigned) assigned to Core-Banking-DBA-L3. PagerDuty alert triggers immediately. Stderr captures full Oracle deadlock logs (ORA-00060). Embeds Runbook KB0041209.

⚠️ Rule B: Cascading Block ➔ Linked Child Ticket (No Alert Storms)

Condition: status == 'BLOCKED_BY_UPSTREAM' (e.g., JOB_04_REG_REPORT).

Action: Generates INC0010406 (Priority: P3 - Moderate, State: On Hold - Awaiting Upstream) assigned to Regulatory-Reporting-L2. Sets parent_incident = INC0010404. Suppresses false alarms: the Regulatory team is informed but not paged into a bridge while the DBA team works on the root failure.

⏱️ Rule C: Recovered Job with SLA Breach ➔ P2 SLA Warning

Condition: status == 'SUCCESS' and sla_breached == 1 (e.g., JOB_02_LEDGER_RECON).

Action: Generates INC0010405 (Priority: P2 - High, State: New) assigned to FinControl-GL-Support-L2. Notes that while the ledger balanced on Attempt 2, the 3.20s duration exceeded the 1.5s SLA window due to transient lock contention, logging a daytime tuning ticket.

5. 15 Tough Interview Cross-Questions & Model Answers ("Grill Me")

Algorithms 1. What happens if an engineer introduces a circular dependency in batch_schedule.json?
Our engine implements Kahn’s algorithm for topological sorting in src/engine.py. It maintains an in-degree map of all dependencies. In a circular dependency, cycle nodes never hit an in-degree of zero and never enter the queue. The engine checks if len(ordered_ids) != len(job_map); if they don't match, it aborts immediately with a ValueError before executing any subprocesses, preventing infinite loops or race conditions.
Database 2. Why did you use SQLite with WAL mode instead of PostgreSQL?
For an on-host batch orchestrator agent (like Control-M Agent or JP1/Agent), local lightweight persistence eliminates network failure risks: if the network or central database goes down, the orchestrator must still record process execution and audit states. Standard SQLite locks the database file during writes; by enabling Write-Ahead Logging (PRAGMA journal_mode = WAL), readers never block writers and writers never block readers, giving high-concurrency ACID persistence with zero server overhead.
Reliability 3. How does your orchestrator handle a process that hangs indefinitely?
In production, we pass a timeout parameter to subprocess.run(..., timeout=timeout_sec). If the job hangs (e.g. frozen network socket), Python raises subprocess.TimeoutExpired. We catch this exception, call proc.kill(), record the status as FAILED with a timeout error, and generate an immediate P1 incident alerting the operations bridge.
Performance 4. Why did you measure wall-clock time instead of CPU execution time for SLAs?
In banking operations, regulatory and settlement deadlines depend on clock time, not CPU execution time. If a job runs for 0.5s, fails, sleeps for 2 minutes on backoff, and runs for 0.5s on retry, CPU time is 1.0s. That looks healthy, but in reality, it delayed the core banking pipeline by over 2 minutes. By computing job_overall_end_dt - job_overall_start_dt, we measure the true latency experienced by the bank.
Testing 5. How does job_02_ledger_recon.py detect attempts idempotently?
We implemented dual-mode attempt detection. When run by the orchestrator, it injects BATCH_ATTEMPT into the subprocess environment. The script checks os.environ.get("BATCH_ATTEMPT"). If "1", it fails with lock contention; if "2", it reconciles and exits 0. If executed standalone from the terminal, it falls back to a persistent JSON state file in data/.job_02_recon_state.json, unlinking it upon successful recovery.
Unix OS 6. Walk me through the Unix commands in system_housekeeping.sh.
We query disk space with df -h / using an awk loop to find the field containing %, ensuring resilience against shifting column formatting across Linux environments. We extract memory from free -m using available memory (column 7) rather than raw free memory to account for buffer/cache. We read CPU load from /proc/loadavg for kernel-level speed, and count zombies using ps aux | awk '$8=="Z"' | wc -l.
Incident 7. If `/var/log` hits 94% disk usage before the EOD batch, what do you do?
First, run df -h to confirm the mount point. Second, run du -ahx /var/log | sort -rh | head -20 to find the largest runaway log files. Third, run lsof +L1 /var/log to check for deleted files still held open by un-bounced processes. Fourth, compress historical logs older than 7 days using find /var/log -type f -name "*.log" -mtime +7 -exec gzip {} \; or truncate active runaway logs using > filename.log. If space is still critical, escalate immediately to the Linux infrastructure team to extend the LVM logical volume before the batch starts.
Unix OS 8. What are zombie processes and how do you kill them?
A zombie process (code Z in ps aux) has finished execution but still occupies a slot in the OS process table because its parent has not called wait(). Because zombies are already dead, kill -9 <pid> does nothing. You must find the parent using ps -o ppid= -p <zombie_pid> and send a SIGCHLD signal (kill -s SIGCHLD <ppid>). If the parent is hung, bouncing the parent causes init (PID 1) to adopt the zombie and reap it.
Architecture 9. Why check mock daemons like `controlm-agent` and `swift-mq-listener`?
In banking batch operations, scripts depend on external middleware. The Control-M agent (port 7005) receives job instructions from the central scheduler, the SWIFT MQ listener connects to IBM WebSphere MQ channels for foreign exchange messages, and the AS400 bridge links to legacy ledger mainframes. Validating active PIDs and ports during pre-flight checks ensures middleware connectivity before initiating high-value settlement.
Operations 10. How do you prevent `logs/batch_engine.log` from filling the disk?
In Python, we configure logging.handlers.RotatingFileHandler(maxBytes=50*1024*1024, backupCount=10) to retain 10 historical 50MB log segments. At the OS level, we configure standard Linux logrotate in /etc/logrotate.d/batchguard with daily, rotate 30, compress, and copytruncate.
Banking 11. Why didn't you auto-retry `JOB_04_REG_REPORT` when it was blocked?
JOB_04 did not fail due to a transient software error; it was halted because upstream EOD settlement suffered an unrecoverable deadlock. In banking, submitting statutory reports (MAS Notice 610, Fed CCAR) against unposted or corrupted ledger data leads to severe regulatory sanctions. Retrying JOB_04 before settlement is resolved would either fail or submit invalid numbers.
Operations 12. If `JOB_03` is fixed by DBAs at 3:15 AM, how do you resume without re-running `JOB_01` and `JOB_02`?
In Control-M or JP1, an operator performs a 'Force Rerun from Failed Job'. In our engine, we support a resume flag: python3 main.py --resume-batch <run_id>. The orchestrator inspects SQLite, verifies that `JOB_01` and `JOB_02` have status `SUCCESS`, bypasses them, and restarts execution directly at `JOB_03`. Once `JOB_03` succeeds, `JOB_04` is automatically unlocked and executed.
ITIL 13. How does parent-child correlation prevent an Alert Storm?
When a core database job fails, dozens of downstream jobs fail or block. If each creates a standalone P1 alert, 30 bridges are paged, creating chaos in the Command Center. Our engine creates one master P1 incident for `JOB_03` (the root cause) and links downstream blocked jobs as child tickets (priority P3, state 'On Hold - Awaiting Upstream'). The operations team focuses on 1 primary incident bridge instead of 30 duplicate alarms.
ITIL 14. Why generate a P2 incident for `JOB_02` if it ended with Exit Code 0?
Because functional success does not equal SLA compliance. `JOB_02` succeeded on Attempt 2, but its duration was 3.20s against a 1.5s SLA window. If multiple jobs experience retry delays, the cumulative lag pushes EOD settlement past domestic clearing cut-offs. Raising a P2 ticket alerts the GL support team during normal business hours to investigate lock contention on GL_BALANCES_STG, preventing future production delays.
Audit 15. How does this shift handover report satisfy MAS and Fed audit requirements?
MAS Technology Risk Management Guidelines and Federal Reserve standards require strict event logging and formal operational handovers. Our engine produces an immutable digital record: pre-batch OS health telemetry, job execution attempt durations and exit codes, cross-referenced ServiceNow ticket numbers, and digital sign-off blocks from outgoing and incoming shift analysts. This replaces error-prone manual shift notes with an auditable automated artifact.
